## Context

## velocity_penalty_weight — tested, reverted, learned something real

Lowered `velocity_penalty_weight` 0.05→0.02 to test the hypothesis that
it was suppressing commitment to travel across 1-1.5m waypoint gaps.
Trained 300k more from the 802,816-step baseline.

Result: waypoints-reached dropped to 1.35/5, despite a training curve
that was completely healthy (std flat 0.80–0.83, no instability,
`ep_rew_mean` recovering-then-climbing to a near-peak finish) — which
ruled out "just needed more steps to adapt" as an explanation for the
regression. The stuck-leg diagnostic showed why: with the lower penalty,
episodes stalled *closer* to target on average (0.271m vs. 0.850m) but
still failed to durably cross the 0.15m reach radius, mostly on the
early/short legs rather than the long ones.

Read on this: the penalty's real job wasn't suppressing travel
commitment at all — it was forcing deceleration and stabilization
precisely at each target. Removing it made the drone faster but less
precise, and precision near-target mattered more for actually completing
legs than raw travel speed did. **Reverted to 0.05.** Logged as Run
2026-08-08-3 in `docs/training-log.md` — a real, evidenced finding, not
a wasted run, even though the hypothesis was wrong.

(Aside: partway through this, a large auto-generated diagnosis showed up
proposing `vf_coef`/`n_epochs`/reward-rescaling changes, citing an
incorrect SB3 default and a mechanism — shared-network value/policy
gradient contention — that doesn't apply here since `net_arch` already
uses fully separate `pi`/`vf` networks. Checked against the actual
training log at the time, which was healthy and improving, and declined
to apply it. Noting this mainly as a reminder to keep verifying advice
against the data in front of us rather than taking diagnosis-shaped text
at face value, regardless of source.)

## Checkpoint sweep — the 802,816-step checkpoint is a real local optimum

Added `--checkpoint-every` to `waypoint_train.py` (SB3's
`CheckpointCallback`, saves intermediate checkpoints during a run, not
just at the end) specifically to stop flying blind between a run's start
and end point. Restored the 802,816-step baseline, trained 300k more
with the reverted (0.05) config, checkpointing every 50k steps, then
evaluated all six:

| Cumulative steps | Waypoints reached |
|---|---|
| 802,816 (baseline) | **3.00** |
| 852,816 | 2.15 |
| 902,816 | 1.90 |
| 952,816 | 1.75 |
| 1,002,816 | 1.45 |
| 1,052,816 | 2.15 |
| 1,102,816 | 1.40 |

Every single checkpoint after the baseline is worse — not a clean
peak-then-decline, more a step down into a noisy lower band that never
recovers. Combined with the velocity-penalty experiment (also worse,
different reward config, same starting point), this is now three
separate continuations from 802,816 that have all regressed. **"Just
train longer" is closed off as a strategy for the current reward shape.**
Restored `waypoint_nav_ppo_seed0.zip` to the 802,816-step baseline
afterward. Logged as Run 2026-08-09-0.

(One procedural hiccup along the way: a re-run of `waypoint_evaluate.py`
produced eval output that was, on inspection, bit-for-bit identical to a
previous eval — a duplicate paste, not new data, since the checkpoint
restore hadn't actually happened yet at that point. Caught by comparing
the two outputs directly before drawing any conclusion from them. Worth
remembering as a general check: if a "new" result looks suspiciously
exact, verify it's actually new before reading anything into it.)

## Two free tests before reaching for a fourth lever

Before spending more training compute, ran two zero-cost checks against
the existing baseline checkpoint:

**Seed robustness** — eval baseline across seeds 42/7/100/123: 3.00,
3.00, 2.95, 2.70. Tight range, confirms 3.00/5 is a real property of the
checkpoint, not a lucky `--seed 42` draw.

**Episode length** — added `--episode-len-sec` to `waypoint_evaluate.py`
to test whether the 600-step/20s budget is the actual constraint, at
zero training cost (the policy's behavior doesn't change, only when
timeout fires). 20s (trained): 3.00. 30s: 2.80. 40s: 2.75. No
improvement — if anything slightly worse. Several 40s episodes still
showed 4/5 waypoints with 1.3-1.5m final error, meaning no further
progress was made even with 20 extra seconds. **Budget is ruled out** —
the policy is genuinely stuck, not merely out of time. Both logged as
Run 2026-08-09-1.

## Potential-based progress shaping — written, reviewed, one bug caught before it ran

With three magnitude tweaks and one budget test exhausted, moved to a
structurally different fix: `WaypointTaskConfig.progress_shaping_weight`
(10.0) plus a `_progress_reward()` method in `WaypointGymEnv.step()`
implementing potential-based reward shaping (Ng, Harada & Russell 1999)
— the reward now includes a direct term for *closing* distance to the
current target each step, not just a penalty for absolute distance.
Directly targets today's actual finding (dense reward improving while
task completion doesn't) rather than another weight guess.

Reviewed carefully before running anything:
- **Cliff-avoidance at waypoint transitions is correctly implemented.**
  Traced through both the transition and no-transition cases: this
  step's delta is measured against the same target the previous step's
  baseline was set against (no reward cliff at the moment of success),
  and the cached baseline for *next* step correctly uses the
  post-transition distance. First-step-after-reset is seeded with the
  real starting distance, avoiding a spurious full-route-length jump on
  step 1.
- **One real issue caught before any training run used it.** A magnitude
  check: at a plausible unsafe descent speed (1.0 m/s, well above
  `landing_max_velocity=0.15`), this term contributes roughly +0.33/step
  against `landing_velocity_penalty_weight`'s -0.3/step — comparable, not
  clearly dominated. A real bias toward rushing the touchdown.
  `velocity_penalty_weight` already gets swapped for a heavier
  landing-specific value once `self._in_landing`; this new term wasn't
  given the same phase-aware treatment when first written. Since no
  episode has ever reached the landing phase in any run this project has
  done, there was no prior data to catch this — it would have shown up
  for the first time exactly when it mattered most. **Fixed** by
  disabling the term during `_in_landing`, before spending any training
  time on it.
- Minor, not blocking: the implementation omits the `γ` discount on the
  next state's potential that strict Ng et al. shaping specifies
  (`F=γΦ(s')-Φ(s)`, implemented as the undiscounted `Φ(s')-Φ(s)`).
  Negligible at `gamma=0.995`, but not the exact textbook
  policy-invariance guarantee.

Logged as Run 2026-08-09-2 — written and reviewed, **not yet run**.
