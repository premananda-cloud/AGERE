## Progress-shaping run — a fourth regression, not a fix

Ran the potential-based progress-shaping experiment from the (confirmed —
see below) 802,816-step baseline:

```
python -m src.training.waypoint_train --init-from model/model_weights/waypoint_nav_ppo_seed0.zip --timesteps 300000 --seed 0 --checkpoint-every 50000
```

Cumulative 1,103,872 steps. Eval (seed 42, 20 episodes): **1.55/5 mean
waypoints reached**, 0% crashes, all 20 failures still `timeout`, closest
stuck-leg approach 0.406m mean.

Still worse than the 3.00/5 baseline. This is now the **fourth** separate
continuation from 802,816 that has regressed it: continued training,
velocity-penalty tweak (0.05→0.02), the checkpoint sweep, and now
potential-based progress shaping — a structurally different fix, not just
another weight guess, and it still didn't help. Read on this: single-lever
reward/training adjustments are exhausted as a strategy here, not just
"train longer." Whatever's actually wrong is not reachable by tuning one
term at a time from this checkpoint. (More on what this means for next
steps below — this finding is a direct input to today's decision.)

## Model registry — built, and immediately caught a real incident

Added `src/model_registry.py`: a content-addressed (SHA256, not path/
filename) registry for waypoint checkpoints. `waypoint_train.py` now logs a
`run` record on every save (config, cumulative steps, parent checkpoint);
`waypoint_evaluate.py` now logs an `eval` record on every run by default
(`--no-tag` to skip). Motivation: paths are mutable — every training run
overwrites `waypoint_nav_ppo_seed0.zip` — so "which checkpoint got 3.00/5"
had become a question only answerable by cross-referencing devlog prose
against file mtimes.

It paid off immediately. Before the run above, evaluating the plain
`waypoint_nav_ppo_seed0.zip` path (no `--init-from`, i.e. "the restored
baseline") gave **1.40/5**, not the expected 3.00/5 — the file on disk was
not actually the 802,816-step baseline anymore, almost certainly because a
training run's final `model.save()` had silently overwritten it since the
last restore. Backfilled the registry by evaluating and hashing all 7 files
in `history/`:

## Decision: pause waypoint nav, pivot to precision hover + disturbance/edge cases

**Made today.** Rationale, combining several threads from the last few
days:

- Waypoint nav is stuck at a local optimum (3.00/5, 0% crashes) that four
  independent fixes — continued training, a reward-weight tweak, a
  checkpoint sweep, and a structural potential-based-shaping change —
  have all failed to beat. The remaining candidates (curriculum, network
  capacity) are bigger, slower experiments, not something to resolve
  before the next demo.
- Hover/stabilize (Stage 3) already works, is demoable today (see above),
  and has an existing, unfinished expansion path already partially built:
  `drone_sim.py` already has `apply_velocity_kick()`/
  `apply_impulse_force()` for disturbance injection, and
  `hover_evaluate_disturbance.py` already exists as an evaluation
  entry point for it. Pushing hover toward genuine precision +
  robustness is a natural continuation of infrastructure that's already
  there, not a new task from scratch.
- This lets waypoint nav get the actual investigation it needs (why is
  802,816 a hard local optimum? curriculum? capacity?) without that
  research blocking the only demoable deliverable in the meantime.

**Waypoint nav is paused, not abandoned.** It stays in the repo as-is;
`waypoint_demo.py`'s segfault fix and the curriculum/capacity questions from
2026-08-09's plan are still open, just not the current priority.

**New direction:** train hover/takeoff/land for extreme precision under
dynamic disturbance and edge cases, rather than the current Stage 3 hold-
station-under-mild-jitter task. Scope not yet defined — see open items and
plan below; this needs its own scoping pass before writing any training
code, the same way waypoint nav got `stage3-push-plan.md` before
implementation started.

## Open question, not yet resolved: instinctive control vs. command override

Raised today, worth carrying forward rather than losing in conversation:
how does a policy that's fundamentally reactive/"instinctive" (a learned
`obs → action` mapping, no explicit reasoning) coexist with wanting
human-issued command override? Initial thinking, to be revisited when
scoping the precision task: this is naturally two separable layers, not one
problem —

1. **Low-level "reflex" layer** (what's already built): the trained policy
   reacting to `pos_error`/velocity/orientation every control step. It
   doesn't know *why* it's going somewhere, just how to reduce the error
   it's given — this is correct and desirable for this layer, not a
   limitation to fix.
2. **Command layer above it**: something that sets *what* the reflex layer
   is chasing, and can preempt it outright. Two versions of "override,"
   both cheap given the current architecture:
   - **Target override** — since `pos_error` is computed against
     `task.target_position` at each step rather than baked into the
     network, retargeting mid-flight (a human/supervisor saying "go here
     instead") needs no retraining — the policy was never trained on an
     absolute location, only on relative error.
   - **Actuator override** — a human/manual command bypassing
     `model.predict()` entirely and calling `apply_action()` directly.
     Already demonstrated today, functionally: `hover_takeoff_land_demo.py`'s
     scripted phases ARE this exact mechanism (a non-policy command source
     driving the sim directly).

Both are structurally already present in the codebase in prototype form; a
real "human override" mode would mostly be formalizing a pattern that
already exists rather than inventing new architecture. Worth designing
properly (a `CommandSource` abstraction? a hard preempt/kill-switch?) as
part of scoping the precision-hover task, not decided today.
