## Repo split

- **`AGERE`** — model building only. PyBullet + Gymnasium. **No PX4, no
  MAVSDK, no network dependency at all.** This is where the RL model gets
  trained and iterated on.
- **`AGERE_sims`** — SITL. PX4 + Gazebo lives here exclusively. This is
  where a trained model gets plugged in and tested against the real flight
  stack.

**The relationship is one-directional by design:** `AGERE` ships a trained
model to `AGERE_sims` for plug-and-test. `AGERE_sims` does not feed
requirements or blockers back into `AGERE`'s development — PX4/SITL
integration issues (networking, MAVLink, offboard mode, etc.) are
`AGERE_sims`'s problem to solve, not something that should slow down or
complicate model training. This is the explicit fix for the
"incompatibility hell" that ate time in the 2026-07-23 session — model
development and flight-stack integration are now fully decoupled, not just
logically separate within one repo.

Practical consequence: the `px4/` (parked) subfolders added to `AGERE` in
the 2026-07-29 session — `src/environments/px4/`, `src/actions/px4/`,
`src/training/train_px4_parked.py` — no longer belong in `AGERE` at all.
That code's natural home is `AGERE_sims`, not a parked corner of this repo.

## Code structure decision (`AGERE/src/`)

Locked in today, written up in full in `docs/code-structure.md`:

- **`actions/`** — action space definitions. Framework-agnostic; describes
  what a network's output means as a physical command, independent of
  whether it's running in PyBullet or (eventually) somewhere else.
- **`environments/`** — **purely PyBullet.** No Gymnasium dependency here.
  This is the physics simulation layer: stepping the sim, applying a
  command, reading back drone state. Deliberately doesn't know what
  `gymnasium.Env`, observation spaces, or reward functions are.
- **`models/`** — network architectures. Unchanged from prior sessions.
- **`policies/`** — algorithm construction (PPO, later others). Unchanged.
- **`training/`** — **owns the Gymnasium wrapping.** This is where a plain
  PyBullet simulation object gets wrapped into a `gymnasium.Env` (action/
  observation spaces, reward, termination logic), and where the training
  loop itself lives.

**Rationale for keeping Gymnasium out of `environments/`:** it keeps the
simulation layer reusable and testable independent of any RL-specific
machinery — reward shaping, episode/termination semantics, and space
definitions are RL concerns, not physics concerns, so they live where the
RL training happens. `environments/` should be usable by, e.g., a future
visualization tool or a non-RL test script without pulling in Gymnasium at
all.
