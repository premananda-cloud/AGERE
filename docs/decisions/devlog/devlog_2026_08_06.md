  `model/model_weights/` directory instead, with tasks told apart by

  compared within a task, not across tasks.
- **`training/gym_wrapper/waypoint_gym_wrapper.py`** (new) —
  `WaypointGymEnv`. Tracks current waypoint index, switches to a landing
  phase once the route completes, terminates (not truncates) on a
  successful soft landing — a deliberate deviation from hover's
  always-`False` termination, since this task has a real endpoint. New
  `hard_landing` truncation reason for fast ground contact.
- **`training/waypoint_train.py`** (new) — training entry point, mirrors
  `hover_train.py`'s flag set, plus `--init-from <checkpoint>.zip` to
  warm-start from an existing checkpoint instead of random init.
- **`training/evaluate/waypoint_evaluate.py`** (already existed from an
  earlier session) — reports success rate, mean waypoints reached, crash
  rate, and a route-vs-landing failure breakdown.

## A design decision reversed mid-session: observation space parity

`WaypointGymEnv` was originally drafted with a 10-dim observation space —
hover's 9 (`pos_error`, `velocity`, `roll/pitch/yaw_error`) plus a
`landing_phase` flag, on the theory that the policy should be told
explicitly which behavioral regime it's in.

This was reversed once weight transfer came up as a goal: SB3's
`PPO.load()` rebuilds the policy network's input layer from the saved
observation shape, so a 9-vs-10 mismatch means a hover checkpoint simply
can't be loaded into a 10-dim waypoint env. Since warm-starting from the
already-converged hover policy is clearly worth more than an explicit
phase flag (the hover policy already knows "minimize position error,
don't move too fast" — most of what waypoint-following needs), the flag
was dropped. `WaypointGymEnv`'s observation space is now shape-identical
to `HoverGymEnv`'s. The landing phase is still tracked internally
(`self._in_landing`) for reward/termination logic — it's just not
exposed to the policy as a dedicated input.

## Runs today

### Sanity run — `waypoint_nav_ppo.zip`

```
python -m src.training.waypoint_train --init-from model/model_weights/hover_stabilize_ppo_seed0.zip --timesteps 5000 --gui
```

~6144 actual steps (one PPO rollout past the 5000 target, `n_steps=2048`).
Purpose was purely pipeline verification — confirm the env runs
end-to-end, waypoints/landing-phase logic triggers, warm-start loads and
saves correctly. It did. Not a real training result; the model this
produced was barely perturbed from the hover starting point and wasn't
kept as anything more than a checkpoint of "did the wiring work."

Note for future reference: with `--init-from` (`reset_num_timesteps=False`),
SB3's `total_timesteps` counter in the training log is cumulative from
the loaded checkpoint's own history, not a fresh count for the current
run — the printed `total_timesteps: 507904` etc. in this run's log reads
confusingly for that reason, but is expected behavior, not a bug.

### Real run — `waypoint_nav_ppo_seed0.zip`

```
python -m src.training.waypoint_train --init-from model/model_weights/hover_stabilize_ppo_seed0.zip --timesteps 300000 --seed 0
```

Full 300k steps (147 iterations × 2048 ≈ 301k on top of the counter
baseline). Final training-log snapshot: `ep_len_mean` 600 (== max
episode length), `ep_rew_mean` -291, `explained_variance` 0.928,
`std` 1.07. Saved to `model/model_weights/waypoint_nav_ppo_seed0.zip`.

`ep_len_mean` sitting exactly at the max is itself informative:
episodes are neither crashing early nor succeeding early — every episode
runs the full clock. Confirmed by the eval run below.

### Eval — `waypoint_evaluate.py`, 20 episodes

```
python -m src.training.evaluate.waypoint_evaluate --model model/model_weights/waypoint_nav_ppo_seed0.zip --episodes 20
```

| Metric | Result |
|---|---|
| Success rate | 0.0% |
| Mean waypoints reached | 2.05 / 5 |
| Crash rate | 0.0% |
| Mean episode reward | -273.5 |
| Failure breakdown | 20/20 never finished the route; 0/20 finished-but-failed-landing; all 20 failures are `timeout` |

**Read on this:** genuinely a good sign mixed with an expected one. The
good sign — **zero crashes**, across 20 episodes with a policy that's
only had 300k fine-tuning steps on a materially harder task than hover.
No `out_of_bounds`, no `tilt`, no `hard_landing`. Stability transferred
cleanly from the hover checkpoint, exactly as hoped.

The expected one — it's not finishing the route. 100% of failures are
plain `timeout`, and the route-vs-landing breakdown shows 0/20 ever even
reached the landing phase. This points at *progress*, not *control*: the
policy hasn't yet learned to commit to covering the 1-2m gaps between
waypoints quickly. Plausible given the warm-start's prior optimization
target (hold station within ~0.3m jitter, not travel confidently toward
a point 1.5m away) and a fairly modest 300k-step fine-tuning budget for
a task with 5x the spatial scope of hover.

Not diagnosed further today — deliberately stopping here to pick this up
fresh tomorrow rather than iterating tired.
