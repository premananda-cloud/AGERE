## What changed

### Repo evaluated: `gym-pybullet-drones`
Read the README (did not clone-and-build blind first — discussed tradeoffs
before touching anything). Confirmed it ships a working single-drone hover
task (`HoverAviary`, `learn.py`/`play.py` examples with SB3 PPO) rather than
requiring a hover env built from scratch.

Then cloned it locally to actually read the source (not just the README)
before integrating:
- `HoverAviary` subclasses `BaseRLAviary`, target fixed at `[0,0,1]`,
  8-second episodes, hardcoded reward `max(0, 2 - ||pos_error||**4)`.
- `ActionType.VEL` gives velocity direction + magnitude, PID-controlled
  internally via `DSLPIDControl` — closest match to the velocity-setpoint
  design from the PX4 track. **Limitation found**: this action type has
  **no yaw-rate control** — `BaseRLAviary`'s VEL handler always targets
  `target_rpy=[0, 0, current_yaw]`, i.e. holds whatever yaw the drone is
  currently at. Fine for pure position-hold; would need `ActionType.PID`
  or a custom action type if yaw stabilization becomes a requirement.
- `ObservationType.KIN` = 12-dim kinematic state (pos, rpy, vel, ang vel),
  matching the observation design already sketched for the PX4 track.
- Confirmed `BaseAviary._housekeeping()` reads `self.INIT_XYZS`/`INIT_RPYS`
  fresh on every `reset()` call — meaning true per-episode start-position
  randomization is possible by mutating those arrays before calling
  `super().reset()`, even though `HoverAviary` doesn't do this itself.

### Project restructured: `backseat_driver_rl/`
Modular `src/` layout (config / actions / environments / policies / models
/ training) built in the previous session, now split into active vs.
parked tracks rather than rewritten in place:

**Active (gym-pybullet-drones):**
- `src/config.py` — added `PyBulletHoverConfig` (sim rates, action/obs type
  strings, target position, episode length, reset jitter, truncation
  bounds, reward weights). Wired into `ProjectConfig` alongside the
  existing (now-parked) PX4 config dataclasses.
- `src/environments/pybullet/hover_env.py` — `ConfigurableHoverAviary`, a
  thin subclass of `HoverAviary`. Leverages their physics/observation/
  action handling as-is; adds config-driven target/episode length, custom
  reward shaping (position error + velocity penalty + action-smoothness
  penalty + survival bonus, closer to the original PX4-track design than
  `HoverAviary`'s default quartic reward), and real per-episode start
  randomization.
- `src/training/train.py` — rewritten entry point, no PX4 connection step,
  `--gui` and `--timesteps` CLI flags added.
- `environment.yml` — added `gym-pybullet-drones` as a pip dependency
  (installed via `git+https://...`, compiles `pybullet` from source —
  flagged that this needs a C compiler / `build-essential`).

**Parked (not deleted), for the later PX4/SITL transplant:**
- `src/environments/px4/` — `px4_interface.py` (MAVSDK bridge) and the
  original hand-built `hover_env.py`, moved as-is into a subfolder with a
  docstring note marking them parked and un-retested.
- `src/actions/px4/velocity_action.py` — the normalized-action-to-velocity-
  setpoint scaling logic built for MAVSDK. Not needed for the active track
  since gym-pybullet-drones' `VEL` action type owns that scaling
  internally.
- `src/training/train_px4_parked.py` — original training script.
- `mavsdk` stays in `environment.yml`, marked as the parked dependency.

`src/policies/ppo_policy.py` and `src/models/networks.py` needed no
changes — designed track-agnostic from the start, work with either env.

  reasonable design carried over from the PX4-track plan, not a
  proven-in-practice one — worth watching the first training curve
  closely rather than assuming it's correct.
